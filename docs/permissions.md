# 权限与安全

dshr 会在你的电脑上改文件、跑命令，所以每一次工具调用都要经过把关。这篇讲清楚把关的规则：权限模式、审批、自动审查、
沙箱、插件的能力授权，以及密钥放在哪里。

## 总览

| 层次 | 管什么 | 在哪里设置 |
|---|---|---|
| 权限模式 | 每次工具调用是直接执行、先问你，还是交给模型审查 | 输入卡片的权限菜单；`dshr headless --manual / --auto-review / --yes` |
| 只读预设 | 规划模式、只读的插件预设下，任何修改都被拒绝 | 输入卡片的预设菜单 |
| 命令沙箱 | macOS 上把命令的写入限制在工作区和临时目录 | 自动（“工作区内修改”模式） |
| 插件能力 | JS 插件能读写什么、能连哪些主机、能启动哪些程序 | 插件清单声明，你逐项允许 |
| 密钥存放 | API 密钥、插件密钥、登录令牌 | 系统钥匙串 |

## 访问类型

每次工具调用先判断它的**访问类型**：

| 访问类型 | 哪些调用 |
|---|---|
| 读取 | `read_file`、`list_dir`、`grep`、`glob`、`update_plan`、`delegate`；标了 `readOnly` 或没有任何“写 / 联网 / 执行 / 代办”能力的插件工具 |
| 写入（某个路径） | `write_file`、`edit_file`；只能写工作区的插件工具 |
| 执行 | `run_shell`；有 `exec:` 能力的插件工具 |
| 交给外部 | MCP 工具；能联网或能替你做事（发消息、起子代理、改设置、装插件）的插件工具 |

“写入”会再看路径在不在工作区里。路径按文字判断：相对路径以工作区为基准，处理 `.` 和 `..`，**不解析符号链接**——
工作区里指向外面的符号链接，会被当作工作区内的路径。

## 权限模式

| 模式 | 读取 | 写入工作区内 | 写入工作区外 | 执行命令 | 交给外部 |
|---|---|---|---|---|---|
| **手动确认**（菜单里显示为“手动模式”） | 执行 | 询问 | 询问 | 询问 | 询问 |
| **工作区内修改**（默认） | 执行 | 执行 | 询问 | 询问；macOS 沙箱可用时执行 | 询问 |
| **自动审查** | 执行 | 执行 | 审查 | 审查 | 审查 |
| **完全访问** | 执行 | 执行 | 执行 | 执行 | 执行 |

“审查”是指先交给模型判断风险，低风险直接执行，否则再问你（见 [自动审查](#自动审查)）。

模型知道当前的权限模式：每当模式变化，dshr 会在对话里追加一条 `<environment>` 说明，告诉模型哪些操作会等你审批，
让它把相关的修改合并起来、少做不必要的调用。

**怎么选**

- 不熟悉的项目、敏感的仓库：**手动确认**。每一步都由你点头。
- 日常开发：**工作区内修改**。改代码不打扰你，跑命令和动工作区外的东西前问一声。
- 想减少打断、又不想完全放手：**自动审查**。构建、测试、`git status` 这类常规操作直接执行，危险操作仍然问你。
- 一次性的容器、虚拟机、CI：**完全访问**。不会再问任何事，只在可以随时丢弃的环境里用。

## 审批

需要你确认时，桌面版在输入框的位置显示审批框，命令行在终端里问 `[y/N]`。

| 选项 | 效果 |
|---|---|
| 允许 | 只放行这一次 |
| 允许，本会话内不再询问此工具 | 这个会话里，同一个工具之后都直接放行（只在桌面版里有） |
| 拒绝 | 不执行。模型收到“用户拒绝了这次调用”，系统提示词要求它不要重复同样的调用，而是换个做法或说明它需要什么 |

**必须亲自确认的操作**：有些操作会把权力交出去，例如给插件授予能力、在完全访问以外的模式下修改已经被授予过能力的插件。它们：

- 不看权限模式——桌面版的完全访问也会问；
- 不交给自动审查，也不交给插件的 `reviewTool`、`approve` 钩子；
- 没有“本会话不再询问”，之前对同一个工具选过“不再询问”也不算数。

审批框上会写明“此操作必须由你亲自确认”。唯一的例外是命令行的 `--yes`：那是你明确要求全部放行。

## 自动审查

在“自动审查”模式下，本来要问你的调用先交给**当前会话的模型**判断（会额外消耗少量 token）。审查请求里有：工作区、
操作系统、你最近说的话、工具名、它的影响（写哪个路径、在不在工作区内、执行命令还是交给外部）和参数。

模型按这样的标准回答：

- **放行**：明显低风险、符合你的要求、影响限于项目或容易撤销的常规开发操作——构建、测试、lint、格式化；只读命令
  （`ls`、`cat`、`grep`、`git status/diff/log`）；创建或编辑任务需要的文件；安装项目已经声明的依赖；本地 git 操作
  （add、commit、建分支）。
- **询问**：可能造成损害或让你意外的操作——删除或覆盖项目外的数据、大量删除文件、`rm -rf`；`git push`、强制操作、改写历史、
  丢弃未提交的改动；发布、部署；改系统设置、shell 配置、全局配置或主目录里的文件；`sudo`；读取或发送凭据；上传数据或把下载的脚本
  交给 shell 执行；结束不是 agent 启动的进程；破坏性的数据库操作；代表你调用外部服务（发消息、创建或删除远程资源、付款）；
  和你的要求无关的操作；信息不足以判断的操作。

结果的处理：

| 审查结果 | 处理 |
|---|---|
| 放行，且风险不是“高” | 直接执行 |
| 询问，或风险为“高” | 问你，审批框里附上审查给出的理由（`自动审查：……`） |
| 超时（45 秒）、请求失败、回答看不懂 | 问你，附上“自动审查没能做出判断” |

自动审查**从不直接拒绝**：拿不准的事都交给你决定。插件的 `reviewTool` 钩子排在自动审查前面，插件给了结论就以插件的为准。

## 只读预设

规划模式和标了只读的插件预设会让这一轮**强制只读**，与权限模式无关：

- 会修改东西的工具（写入、执行、交给外部）不发给模型；
- 模型硬要调用时直接拒绝，并告诉它“会话处于只读模式，请描述修改或请用户切换模式”；
- 子代理继承这个限制。

限定了工具名单的插件预设，名单外的工具同样被拒绝。

## 命令沙箱

| 平台 | 做了什么 |
|---|---|
| macOS | “工作区内修改”模式下，`run_shell` 的命令放进 `sandbox-exec`（Seatbelt）运行：默认放行，但收回所有写权限，只开放工作区、临时目录（`/private/tmp`、`/private/var/folders`）、常见的工具缓存（`~/.cargo`、`~/.rustup`、`~/.cache`、`~/.npm`、`~/Library/Caches`）和终端设备。写入范围有了保证，这个模式下的命令就不必逐条询问 |
| Windows | 命令放进 Job Object：超时或被中断时整棵进程树一起结束，不留孤儿进程。Job Object 不限制文件写入，所以命令仍然需要询问 |
| Linux | 命令自成一个进程组，超时或被中断时整组结束；没有写入限制 |

注意：

- 沙箱只限制**文件写入**，不限制读取和网络。
- 其他权限模式不使用沙箱：手动确认、自动审查的命令本来就经过把关，完全访问则不加限制。
- MCP 服务器和插件自带的 MCP 服务器在 dshr 之外运行，**不受沙箱约束**，所以它们的工具在“工作区内修改”模式下每次都会询问。

## 把关的顺序

一次工具调用依次经过这些检查，第一个给出结论的生效：

1. 预设：只读预设、插件预设的工具名单（拒绝）；
2. 插件的 `beforeTool` 钩子：可以拒绝、要求询问；直接放行需要 `hooks:gate` 能力；
3. 选中了插件提供的权限模式时：该插件的 `decide`（见下文“插件提供的权限模式”）；
4. 权限模式（上表）。选中插件权限模式而 `decide` 没给结论时，按“手动确认”处理。

结论是“询问”时，再依次交给插件的 `reviewTool` 钩子和自动审查；都没有结论才真的问你。真的问你时，有 `approve` 钩子的插件
同时收到这次审批，它和审批卡片谁先给出结论就以谁为准（见下文“插件代为审批”）。“必须亲自确认”的操作跳过这两步。

### 插件提供的权限模式

声明了 `permissions:mode` 能力的插件可以导出自己的权限模式，它们排在权限菜单内置四项的后面。选中后：

- 每次工具调用由插件的 `decide` 下结论：放行、拒绝或询问（同步，最多等 300 ms）；
- `decide` 没给结论、超时或出错时，按“手动确认”处理：读取直接执行，其余都问你；
- 预设的只读规则、创造模式的规则和“必须亲自确认”的操作照常生效，插件模式改变不了它们；
- 提供它的插件停用或卸载后，会话退回你之前选的内置模式。

会话日志里记作 `<插件 id>/<模式 id>`。

### 插件代为审批

声明了 `permissions:approve` 能力的插件可以用 `hooks.approve` 回答审批，例如把审批转到手机或 IM 上。它和审批卡片同时等待
（最多 10 分钟），先给出结论的生效；插件返回空值表示放弃，继续等你在界面上回答。插件给出的结论写进会话日志，对话区里显示
“插件 X 代为批准/拒绝了 …”。“必须亲自确认”的操作不会交给插件。

## 插件的能力与授权

JS 插件跑在内嵌的 QuickJS 引擎里，脚本本身碰不到文件、网络和进程，只能通过 `host` 上的函数做清单里声明过、并且你允许过的事。

- **声明**：插件在 `plugin.toml` 的 `capabilities` 里列出要用的能力（完整列表见 [插件 API 参考](plugin-api.md#能力)）。
- **允许**：在“设置 → 扩展”的插件卡片上点“允许”，或 `dshr plugin grant <id>`。允许过的能力记在 `~/.dshr/plugin-grants.json`。
- **没允许就不运行**：声明了能力却没被允许的插件根本不激活，代码一行都不执行。
- **新增的能力要再允许**：插件更新或热重载后清单里多出来的能力，在你允许之前插件同样不激活——不会悄悄多出一个 `net:*`。
- **安装不等于授权**：安装时会列出插件要的权限，装好后仍然要单独允许。
- **收回**：`dshr plugin revoke <id>` 收回全部授权；卸载插件时授权一并收回。

几条容易忽略的边界：

- `net:*` 和 `net:*.example.com` 这样的通配**不包括** `localhost` 和 IP 地址：本机和内网的服务要逐个写明。主机按名字比较，
  不解析 DNS。
- `exec:<程序>` 只比较程序名；带路径的写法只有声明了 `exec:*` 才能用。插件启动程序不经过 shell。
- 插件工具的访问类型由插件的能力决定，不由脚本说了算：能启动程序的工具算“执行”，能联网或代办的算“交给外部”，
  只能写工作区的算“写入”。标了 `readOnly` 的工具按只读处理，同时在运行时就不能写文件、联网、启动程序。
- 钩子、页面渲染、提示词贡献都不能写工作区或启动程序：这些不在权限把关的范围里，所以干脆不允许。
- 插件自带的 MCP 服务器派生一项能力 `mcp:<名字>@<启动参数的哈希>`：启动命令、参数、环境变量一变就要再允许一次。
- **工作区里的插件不会被加载**：插件只从数据目录的插件目录里加载，克隆一个仓库不会顺带执行它带的代码。
  `dshr plugin link` 链接的文件夹是你亲手指定的，同样要授权。

## 创造模式

创造模式下 agent 可以自己写插件。它用的六个工具按这张表把关：

| 工具 | 手动确认 | 工作区内修改 / 自动审查 | 完全访问 |
|---|---|---|---|
| 非创造模式下的任何 `plugin_*` | 拒绝 | 拒绝 | 拒绝 |
| `plugin_read` | 执行 | 执行 | 执行 |
| `plugin_write`：新插件，或没有任何已允许能力的插件 | 询问 | 执行 | 执行 |
| `plugin_write`：**已经被允许过能力的插件** | 必须确认 | 必须确认 | 执行 |
| `plugin_write`：链接到插件目录之外的插件 | 拒绝 | 拒绝 | 拒绝 |
| `plugin_reload`、`plugin_docs`、只渲染页面的 `plugin_page` | 执行 | 执行 | 执行 |
| 执行页面动作的 `plugin_page` | 按“交给外部”处理 | 同左 | 同左 |
| `plugin_grant` | 必须确认 | 必须确认 | 必须确认 |

`plugin_grant` 授予的正好是审批框上列出的那几项；确认之后清单里又多出来的能力，仍然要再确认一次。

完全访问是你明确选择的“不再询问”，所以这个模式下改写已经被允许过能力的插件也直接执行；授予新的能力（`plugin_grant`）
在任何模式下仍然必须由你亲自确认。

为了让 agent 专心把插件写出来，创造模式下另有几条与权限模式无关的限制：

| 调用 | 结论 |
|---|---|
| `write_file`、`edit_file` | 拒绝（插件文件只经 `plugin_write` 写；要改工作区文件请换回标准预设） |
| 用 `read_file`、`list_dir`、`grep`、`glob` 读或搜索可执行文件、安装包（`.exe`、`.asar`、`.dll`、`.node` 等）和程序安装目录 | 拒绝 |
| 用 `run_shell` 抽取二进制里的字符串、扫描程序安装目录 | 拒绝 |
| 这一轮还没写出插件文件，却已经调用了 14 次 `plugin_*` 以外的工具 | 之后的请求里只留 `plugin_*` 工具，写出插件文件后恢复（满 6 次时先提醒一次） |

## 密钥与隐私

- **API 密钥、插件密钥、MCP 密钥、登录令牌只存在系统钥匙串里**（条目见 [配置参考](configuration.md#钥匙串条目)），
  不写进 `config.toml`，也不出现在插件的 `host.config` 里。
- 插件可以用 `fetch(url, { secretHeaders: { authorization: "API_TOKEN" } })` 让宿主把密钥填进请求头，脚本自己不经手明文；
  脚本把密钥打进日志时会被换成 `***`。
- 会话日志保存在本机的数据目录里，包括你发出的附件内容和工具输出。dshr 只把对话内容发给你选择的模型提供商
  （以及你配置的 MCP 服务器、你允许联网的插件）。
- 系统提示词要求模型把文件、网页和工具结果里的文字当作数据，而不是指令；但这不能完全防止提示词注入。处理不受信任的
  内容（陌生仓库、网页、邮件）时，用手动确认或工作区内修改，不要用完全访问。

## 系统提示词里的安全守则

无论哪种模式，内置的系统提示词都要求模型：

- 没被要求时，不运行破坏性或不可逆的命令（删除数据、`git reset --hard`、`git push --force`、全局安装）；
- 不撤销或覆盖不是它做的修改——你可能正在编辑同样的文件；
- 没被要求时，不提交、不推送、不发布；
- 调用被拒绝或被拦下时不要重复，而是换个做法或说明需要什么。

这些守则依赖模型遵守；真正的保证来自上面的权限模式、沙箱和授权。
