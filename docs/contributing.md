# 协作规范：Issue、PR 与版本号

这篇规定 dshr 仓库里 Issue 怎么提、PR 怎么开与合并、版本号怎么定、Release 怎么发。
构建、测试与代码约定见 [开发与贡献](development.md)。

## 1. 分支

| 分支 | 用途 |
|---|---|
| `main` | 已发布或可发布的代码。只通过 PR 合入，不直接推送 |
| `dev` | 日常开发的集成分支，定期以 PR 合入 `main` |
| `fix/<简述>` | 单独的缺陷修复，例如 `fix/high-contrast-selected-yellow` |
| `feat/<简述>` | 单独的新功能，体量较大或需要单独评审时使用 |
| `docs/<简述>` | 只改文档 |
| `release/vX.Y.Z` | 可选：发布前冻结、只收修复时使用 |

分支名用小写英文与连字符，不用中文和空格。

## 2. Issue

### 2.1 类型

用 `.github/ISSUE_TEMPLATE/` 里的模板提交，空白 Issue 只用于讨论。

| 模板 | 标签 | 适用 |
|---|---|---|
| 缺陷报告 | `bug` | 行为与文档或预期不符、崩溃、界面显示错误 |
| 功能建议 | `enhancement` | 新功能、现有功能的改进 |
| 文档问题 | `documentation` | 文档错误、缺失或过时 |

### 2.2 标题

标题用中文写成一句完整的陈述，说明“哪里、出了什么问题”或“希望做到什么”，不加句号，不写“求助”“急”之类的字样。

- 缺陷：`[范围] 现象`，例如 `[桌面版] 高对比度下工具卡标题悬停时文字看不清`
- 建议：`[范围] 希望……`，例如 `[插件] 希望插件页面支持表格节点`

范围取下列之一：`桌面版`、`命令行`、`Agent`、`模型`、`工具`、`权限`、`MCP`、`Skills`、`插件`、`配置`、`会话`、`界面`、`文档`、`构建`。

### 2.3 内容要求

缺陷报告必须包含：

1. **版本**：“设置 → 关于”或 `dshr --version` 显示的版本号；从源码构建时附上提交哈希。
2. **环境**：操作系统及版本、使用的提供商与模型、权限模式。
3. **复现步骤**：从启动开始，逐步写出；能用演示模型（`DSHR_PROVIDER=demo`）复现的注明。
4. **预期结果与实际结果**。
5. **日志或截图**：命令行版附 `DSHR_LOG=debug` 的输出。

附带的日志、截图、配置**必须去掉 API 密钥、令牌和个人路径**。安全漏洞不要公开提交 Issue，请通过 GitHub 的私密漏洞报告（Security → Report a vulnerability）提交。

### 2.4 标签

| 类别 | 标签 |
|---|---|
| 类型 | `bug`、`enhancement`、`documentation`、`refactor`、`performance`、`chore` |
| 状态 | `needs-info`（等待补充信息）、`confirmed`（已确认）、`wontfix`、`duplicate` |
| 版本影响 | `breaking`（破坏性更改，见 §4.2）、`behavior-change`（兼容但改变可观察的行为） |
| 平台 | `windows`、`macos` |

关闭 Issue 时写明原因：已由哪个 PR 修复，或为什么不处理。重复的 Issue 关联到原 Issue 后关闭。

## 3. Pull Request

### 3.1 范围

- 一个 PR 只解决一件事。`dev` 合入 `main` 的汇总 PR 除外，但标题要概括其中最主要的变更。
- 修复与重构分开提交；纯格式调整不与功能改动混在一起。
- 关联的 Issue 在描述里写 `Closes #编号` 或 `Refs #编号`。

### 3.2 标题

标题用中文，说明这个 PR 带来的结果，不加句号，不超过 50 个汉字。必要时用冒号引出范围：

- `修复 Windows 下 run_shell 引号与 $ 被破坏，并增加 PowerShell 模式`
- `插件页面：新增控件、布局与展示节点，支持尺寸与更多样式`
- `内置高对比度配色：选中底色改为 #F2DA00`

不写“更新代码”“一些修改”之类无法判断内容的标题。发版本的 PR 与其提交一致，写作 `chore: 版本号更新至 X.Y.Z`（见 §5）。

### 3.3 描述

按 `.github/pull_request_template.md` 填写：

- **变更内容**：做了什么、为什么这样做；改动界面的附浅色 / 深色截图。
- **影响范围**：涉及的 crate、配置项、插件 API、会话日志格式。
- **破坏性更改**：有则写明变更前、变更后与影响范围，并加 `breaking` 标签。
- **行为变更**：不破坏兼容性、但会改变可观察行为的（默认值、默认快捷键、显示内容等），单独列出并加 `behavior-change` 标签。

这两部分在发布时直接整理进 Release 说明（见 §5.2），请写成可以直接引用的完整句子。
- **测试**：运行了哪些测试，手动验证了哪些场景。
- **检查清单**：与 [开发与贡献 · 提交前](development.md#提交前) 一致。

### 3.4 提交信息

- 提交说明用中文，第一行概括改动，不加句号，正文按需说明原因。
- 版本号变更的提交写作 `chore: 版本号更新至 X.Y.Z`。
- 一个提交保持可编译、测试可通过。

### 3.5 评审与合并

- CI（`fmt`、`clippy -D warnings`、Linux / Windows / macOS 测试、`cargo-deny`）全部通过后才能合并。
- 至少一位维护者批准；作者本人是唯一维护者时，合并前自查一遍检查清单。
- 评审意见逐条回复：已修改的说明在哪个提交，不采纳的说明理由。
- `fix/*`、`feat/*` 等短期分支用 Squash 合并，合并后删除分支；`dev` 合入 `main` 用普通合并，保留提交历史。

## 4. 版本号

### 4.1 格式

版本号遵循 [语义化版本 2.0.0](https://semver.org/lang/zh-CN/)：`主版本号.次版本号.修订号`，例如 `0.2.0`。

- **唯一来源**是根 `Cargo.toml` 的 `[workspace.package] version`，所有 crate 通过 `version.workspace = true` 继承，不在单个 crate 里另写版本。
- 程序里显示的版本、MCP 握手里的 `clientInfo.version`、插件 `[engines] dshr` 的比较都取自这里（`CARGO_PKG_VERSION`），因此改版本号只需改这一处，并同步 `Cargo.lock`（`cargo check` 即可更新）。
- Git 标签写作 `v` 加版本号：`v0.2.0`。预发布版本加后缀：`v0.3.0-beta.1`、`v0.3.0-rc.1`，后缀依次为 `alpha`、`beta`、`rc`，序号从 1 开始。

### 4.2 递增规则

1.0.0 之前（当前阶段）：

| 变更 | 递增 | 示例 |
|---|---|---|
| 破坏性更改：插件 API 移除或改变行为、`config.toml` 字段改名或删除、命令行参数改变、会话日志无法被旧版本读取 | 次版本号 | `0.2.3` → `0.3.0` |
| 新功能、新的配置项或插件 API，旧的写法仍然可用 | 次版本号 | `0.2.3` → `0.3.0` |
| 只有缺陷修复、性能改进、文档与界面细节调整 | 修订号 | `0.2.3` → `0.2.4` |

1.0.0 之后：破坏性更改递增主版本号，向后兼容的新功能递增次版本号，修复递增修订号。

判断是否“破坏性更改”时，以下内容视为公开接口：

- 插件 API（[插件 API 参考](plugin-api.md) 列出的 `host` 成员、导出项、界面节点、能力名）；
- `config.toml` 的字段与取值、环境变量、`keybindings` 与配色方案文件格式；
- `dshr` 命令行的子命令、参数与退出码；
- 各 crate 对外的 Rust 接口（类型、字段、函数签名）。crate 虽不发布到 crates.io，派生分支与 Rust 侧插件仍依赖它们；
- 会话日志 `session.v1.jsonl` 的事件格式。日志格式本身的破坏性更改还要提升文件名中的版本（`v1` → `v2`），并保留读取旧格式的代码。

插件作者依据这些规则写 `[engines] dshr`，例如 `">=0.2, <0.3"`，因此破坏性更改不能只放在修订号里。

## 5. Release

### 5.1 发布流程

1. 在 `dev` 上把根 `Cargo.toml` 的版本号改为新版本，运行 `cargo check` 更新 `Cargo.lock`；依赖有变化时重新生成 `THIRD_PARTY_NOTICES.md`。
2. 同步 `README.md` 里写到的“当前版本”。
3. 提交 `chore: 版本号更新至 X.Y.Z`，以同样的标题开 PR 合入 `main`，等待 CI 通过后合并。
4. 在 `main` 的合并提交上打附注标签并推送：

   ```bash
   git tag -a vX.Y.Z -m "DSHR-vX.Y.Z"
   git push origin vX.Y.Z
   ```

5. 基于该标签创建 GitHub Release，按 §5.2 填写。

已发布的标签不移动、不删除。发布后发现问题时，修复后发布新的修订版本。

### 5.2 Release 标题与说明

**标题**为 `DSHR-vX.Y.Z`，与 `DSHR-v0.1.0`、`DSHR-v0.2.0` 一致。带 `-alpha`、`-beta`、`-rc` 后缀的版本勾选“Set as a pre-release”。

**说明**以 [DSHR-v0.2.0](https://github.com/EPLCX/dshr/releases/tag/v0.2.0) 为范本，按以下顺序分为五节，节与节之间用 `---` 分隔；某一节没有内容时整节省略：

| 节 | 内容 | 下级分组（`###`） |
|---|---|---|
| `## 破坏性更改` | 需要用户、插件作者或下游代码做出调整的变更 | `### 一、插件 JS API 与清单`、`### 二、Rust 接口`，必要时增加配置、命令行、会话日志等，按中文序号编排 |
| `## 功能更新` | 新增功能与改进 | 按范围：`### 桌面版`、`### 命令行`、`### 插件 API`、`### 创造模式`、`### 构建与发布` 等 |
| `## 问题修复` | 缺陷修复 | 按范围：`### 安全`、`### 辅助功能`、`### 插件`、`### 登录`、`### 构建、测试与 CI` 等；安全放在最前 |
| `## 行为变更` | 不破坏兼容性、但会改变可观察行为的变更 | 不分组，开头写“以下变更不破坏兼容性，但会改变可观察的行为：” |
| `## 文档` | 新增或更新的文档 | 不分组 |

各节条目的写法：

- **破坏性更改**：每项以加粗的编号标题开头（如 `**1. 钩子参数中 `session` 字段的语义变更（子代理场景）**`），下列“变更前”“变更后”“影响范围”三条；规则较多时用表格列出。Rust 接口的变更用“位置 / 变更”两列的表格，表后说明下游代码需要怎样调整。
- **功能更新**：每个功能以加粗的短标题开头（如 `**按标题搜索会话**`），下列要点：入口与默认快捷键（附动作名）、交互方式、限制与上限、对应的配置项、无障碍支持。
- **问题修复**：每项以加粗的现象描述开头，以句号结尾（如 `**Windows 上 `host.exec` 每次运行外部程序均弹出控制台窗口。**`），随后说明原因与修复方式。依赖的安全公告写明版本变化与公告编号（如 `url` 2.5.8 → 2.5.9，修复 RUSTSEC-2026-0592）。
- **行为变更**、**文档**：每条一句完整的陈述。

用语要求：

- 使用书面语，从用户能观察到的结果来写，不照抄提交信息，不写 PR 编号。
- 配置项、字段、函数、快捷键、文件名一律用代码格式；数值写明单位。
- 术语与文档保持一致：“破坏性更改”“行为变更”“问题修复”，不混用“不兼容变更”“Bug 修复”等其他说法。

可以先用“Generate release notes”按 `.github/release.yml` 列出本次合入的 PR 作为素材，再按上述结构改写，不直接发布自动生成的列表。

### 5.3 构建产物

需要附带构建产物时，必须从该版本标签对应的提交构建，并与 `LICENSE`、`THIRD_PARTY_NOTICES.md` 一起分发：macOS 用 `scripts/bundle-macos.sh`，Windows 用 `cargo build --release -p dshr-desktop -p dshr-cli`（见 [开发与贡献 · 打包](development.md#打包)）。
